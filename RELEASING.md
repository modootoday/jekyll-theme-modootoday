# Releasing

The first release is **1.0.0** (tag `v1.0.0`). No earlier version was published; the 0.x milestones are only recorded under "Pre-release history" in `CHANGELOG.md`.

Releases are published only from a `v*` tag by `.github/workflows/release.yml`, through the protected `rubygems` environment (a maintainer approves the run) and RubyGems trusted publishing (OIDC, no API key).

## Checklist

1. **Version.** Check the packaged files with `gem build` and `gem spec jekyll-theme-modootoday-X.Y.Z.gem files` (only `_layouts`, `_includes`, `_sass`, `assets`, `exe`, `lib`, `i18n`, LICENSE, READMEs, RULES.md and CHANGELOG.md; no `.spec/`, `RELEASING.md`, `docs/`, `example/`, `script/` or `test/`). `spec.version` in the gemspec, the `## [X.Y.Z]` heading and link in `CHANGELOG.md`, and the install snippets in `README.md`, `README.ko.md`, `docs/guides/install.md`, `docs/index.md` and their `ko/` pages agree (`test/project/version_test.rb` enforces this). After changing `spec.version`, run `script/version-include`: it regenerates `_includes/modootoday/version.html`, whose `mt_version` is the `?v=` query on theme asset URLs, and the same test fails while it is stale.
2. **Changelog.** Change `## [X.Y.Z] - Unreleased` to `## [X.Y.Z] - YYYY-MM-DD` (for 1.0.0: `## [1.0.0] - YYYY-MM-DD`); list public API changes (see the public API page). Point the `[X.Y.Z]` link at the tag (`…/releases/tag/vX.Y.Z`) and add `[Unreleased]: …/compare/vX.Y.Z...HEAD` with an empty `## [Unreleased]` section.
3. **Release check green on `main`** with no warnings. Pushes to `main` run only the fast jobs, so start the slow ones by hand on the release commit: `gh workflow run ci.yml`, `gh workflow run lighthouse.yml` and `gh workflow run visual.yml`. The CI run covers the GitHub Pages stack, Jekyll 4 (oldest and newest Ruby), the Jekyll 3.9 floor, JS, tokens and docs QA; Lighthouse checks the budget (median of 3 runs); Visual regression reports every difference from the latest release tag, and each one must be intended.
4. **Visual review.** Open the docs site and the kitchen sink in light and dark at phone and desktop widths, in English, Korean and Japanese; compare with the QA screenshots artifact. Every component example is checked at element level: each example section of the Components index, the kitchen sinks and the recipes with examples is shot on its own (English light and dark at 360 and 1440, Korean and Japanese light at 360) and looked at next to its source, and the docs QA component audit (`test/system/audit/features/components.mjs`) and `test/system/docs/examples.rb` report nothing. A whole-page look misses a broken example. `RULES.md` says `md-components v1` and Status final (done 2026-10-30).
5. **Trusted publisher.** On rubygems.org, the gem (or, before the first release, a *pending* trusted publisher) must point at this repository, workflow `release.yml` and environment `rubygems`. For 1.0.0 this is the pending publisher: open rubygems.org → Trusted publishers and check it is still listed and not expired (a pending publisher expires if no gem is pushed in time); register it again with the same values if it has.
6. **Tag.** `git tag vX.Y.Z && git push origin vX.Y.Z` (first release: `git tag v1.0.0 && git push origin v1.0.0`). The workflow checks that the tag equals the gem version.
7. **Approve** the `rubygems` environment deployment when the run asks for it.
   After the gem is pushed, the same run creates the GitHub Release for the tag, with the `## [X.Y.Z]` entry of `CHANGELOG.md` as the notes (`ruby script/release-notes vX.Y.Z` prints them; run it before tagging to check). It skips the step when the Release already exists.
8. **After release.** Check the gem page and the GitHub Release. The docs site stays on `remote_theme: …@main`, because it documents and demonstrates `main` (adr:modootoday/20261105073859); the install examples, README and starters carry the release pin.
9. **Starters.** The published starters are gitlinks in `example/` to their own repositories (adr:modootoday/20261104171142). A starter pins only released tags and the theme's release never waits for one, so after the gem is out:
   1. In each starter's repository (`cd example/<name>`, on `main`), merge `next` if it has commits.
   2. From the theme checkout at the tag, run `bundle exec rake starters:render[<name>]`: it moves the `remote_theme` pin and the `Gemfile` line to `vX.Y.Z` and refreshes the files the theme renders in the work tree.
   3. Commit `chore: theme vX.Y.Z` there and push `main`; the starter's Pages workflow redeploys its demo. Check the demo once it is green.
   4. In the theme repository, one commit `chore(starters): pin starters to vX.Y.Z` moves every gitlink; `rake starters:check` must pass with no pin warning.

   Until then `rake starters:check` warns that the pins are behind the gemspec version. A starter that is not published yet stays a plain folder rendered into `pkg/starters/<stack>/<name>/`.
