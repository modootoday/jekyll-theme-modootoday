# Releasing

The first release is **1.0.0** (tag `v1.0.0`). No earlier version was published; the 0.x milestones are only recorded under "Pre-release history" in `CHANGELOG.md`.

Releases are published only from a `v*` tag by `.github/workflows/release.yml`, through the protected `rubygems` environment (a maintainer approves the run) and RubyGems trusted publishing (OIDC, no API key).

## Checklist

1. **Prepare.** With a clean tree on `main` and `npm ci` done, run `script/release-prep X.Y.Z` (adr:modootoday/20261109225836). It writes the `## [X.Y.Z] - YYYY-MM-DD` entry of `CHANGELOG.md` from the commits since the last tag with git-cliff (see CONTRIBUTING, "Commits and the changelog"), empties `## [Unreleased]` and moves the link definitions; sets `spec.version` and the install pins of the nine files `script/release/pins.rb` lists (`test/project/version_test.rb` checks them); regenerates `_includes/modootoday/version.html` (`mt_version`, the `?v=` query on theme asset URLs) and the release list of the docs Changelog page (`ruby script/docs-index`); and checks the gem's file list (only `_layouts`, `_includes`, `_sass`, `assets`, `exe`, `lib`, `i18n`, LICENSE, READMEs, RULES.md and CHANGELOG.md).
2. **Changelog.** The entry holds two `<!-- release-prep: ... -->` placeholders, the only hand-written parts: the `Visual:` line, which names the intended differences the visual run reports against the last release (or says there are none), and a one-paragraph summary of the release. Read the generated lines too: a line that reads badly is fixed here, before the tag. `test/project/changelog_test.rb` checks the Keep a Changelog sections and their order (Added, Changed, Deprecated, Removed, Fixed, Security), the dated headings, the link definitions, the `Visual:` line and that no placeholder is left, and fails when a released entry differs from the one in its tag. Commit (`git commit -am 'chore(release): X.Y.Z' -m 'Changelog: none'`) and push.
3. **Release check green on `main`** with no warnings. Run `script/release-prep X.Y.Z` again on the pushed release commit: it refuses while a placeholder is left, then starts the slow workflows by hand on that commit (`gh workflow run` for `ci.yml`, `lighthouse.yml`, and `visual.yml` with `base=` the previous tag). `script/release-status` prints the three runs on HEAD in one table. A later push does not cancel these manual runs, and a second manual run of the same workflow on the same branch waits for the first. The CI run covers the GitHub Pages stack, Jekyll 4 (oldest and newest Ruby), the Jekyll 3.9 floor, JS, tokens and docs QA; Lighthouse checks the budget (median of 3 runs); Visual regression reports every difference from the previous release tag, and each one must be intended.
4. **Visual review.** Open the docs site and the kitchen sink in light and dark at phone and desktop widths, in English, Korean and Japanese; compare with the QA screenshots artifact. Every component example is checked at element level: each example section of the Components index, the kitchen sinks and the recipes with examples is shot on its own (English light and dark at 360 and 1440, Korean and Japanese light at 360) and looked at next to its source, and the docs QA component audit (`test/system/audit/features/components.mjs`) and `test/system/docs/examples.rb` report nothing. A whole-page look misses a broken example. `RULES.md` says `md-components v1` and Status final (done 2026-10-30).
5. **Trusted publisher.** On rubygems.org, the gem (or, before the first release, a *pending* trusted publisher) must point at this repository, workflow `release.yml` and environment `rubygems`. For 1.0.0 this is the pending publisher: open rubygems.org → Trusted publishers and check it is still listed and not expired (a pending publisher expires if no gem is pushed in time); register it again with the same values if it has.
6. **Tag.** `git tag vX.Y.Z && git push origin vX.Y.Z` (first release: `git tag v1.0.0 && git push origin v1.0.0`). The workflow first checks the release check of step 3 on the tagged commit: it stops before anything is published unless the newest manual run of each of `ci.yml`, `lighthouse.yml` and `visual.yml` on that commit succeeded (`script/release-status SHA --verify`). Then it checks that the tag equals the gem version.
7. **Approve** the `rubygems` environment deployment when the run asks for it.
   After the gem is pushed, the same run creates the GitHub Release for the tag, with the `## [X.Y.Z]` entry of `CHANGELOG.md` as the notes (`ruby script/release-notes vX.Y.Z` prints them; run it before tagging to check). It skips the step when the Release already exists.
8. **After release.** Check the gem page and the GitHub Release. The docs site stays on `remote_theme: …@main`, because it documents and demonstrates `main` (adr:modootoday/20261105073859); the install examples, README and starters carry the release pin.
9. **Starters.** The published starters are gitlinks in `example/` to their own repositories (adr:modootoday/20261104171142), and they update themselves; no token is stored anywhere (adr:modootoday/20261109225836). A starter pins only released tags and the theme's release never waits for one:
   1. Each starter repository runs its **Theme update** workflow (`.github/workflows/theme-update.yml`, rendered by `rake starters:render`) daily. It reads the theme's latest release from the public GitHub API; when that is newer than the `remote_theme` pin, it checks out the theme at that tag, runs `rake starters:render[<name>,DIR]` on the starter's `main`, commits `chore: theme vX.Y.Z` with the repository's own `GITHUB_TOKEN` and deploys its Pages site in the same run (a `GITHUB_TOKEN` push starts no other workflow). It runs only in the starter's own repository, so a site made from the template never rewrites itself. For an immediate update, run it by hand: `gh workflow run theme-update.yml --repo <starter repository>`. Check each demo once it is green.
   2. If a starter has commits on `next` that should ship with the release, merge them into its `main` first.
   3. The theme's **Starter gitlinks** workflow (`.github/workflows/starter-gitlinks.yml`) runs daily, moves every `example/<name>` gitlink to its starter's `main`, runs `rake starters:render starters:check starters:build` in the same job and commits `chore(starters): move the starter gitlinks to their main` with the theme's own `GITHUB_TOKEN`. Run it by hand for an immediate move: `gh workflow run starter-gitlinks.yml`.
   4. Fallback, from a theme checkout at the tag with the maintainer's own git credentials: `bundle exec rake starters:publish` (or `starters:publish[<name>]`) re-renders each published starter on its repository's `main`, commits `chore: theme vX.Y.Z` there and pushes it.

   Until the gitlinks move, `rake starters:check` warns that the pins are behind the gemspec version. A starter that is not published yet stays a plain folder rendered into `pkg/starters/<stack>/<name>/`.

## Overriding the release check

The release workflow publishes nothing while the release check of the tagged commit is not green. When a run failed for a reason outside the release (a runner outage, a flaky external download) and the maintainer has decided to release anyway, set a repository variable to the tag and re-run the failed workflow run:

```sh
gh variable set RELEASE_CHECKS_OVERRIDE --body vX.Y.Z
gh run rerun <run id> --failed
```

The step then prints the table, warns that the check was overridden, and continues. The variable names one tag, so it does not carry over to the next release; delete it afterwards (`gh variable delete RELEASE_CHECKS_OVERRIDE`) and say why in the release's summary paragraph.

## Dependency updates

Dependabot (`.github/dependabot.yml`) opens weekly pull requests for GitHub Actions, npm and bundler, only for releases at least two weeks old (`cooldown: {default-days: 14}`, the practice of adr:modootoday/20261105101229). The GitHub Pages set (`github-pages`, `nokogiri`) stays ignored, because `gemfiles/github-pages.gemfile` pins the production versions on purpose, and so do `jekyll-titles-from-headings` and `jekyll-optional-front-matter`: they are development pins that mimic GitHub Pages, which supplies its own versions (adr:modootoday/20261110020841). They are the one pull request flow this repository keeps: `.github/workflows/dependabot-auto-merge.yml` squash-merges each one when the latest run of every workflow that runs on pull requests has passed or been skipped on its head commit, and its `build(deps)` subject keeps it out of the CHANGELOG (adr:modootoday/20261109225836). The workflow starts when any of those workflows completes (`test/release/dependabot_test.rb` fails when one is missing from its trigger list) and judges only the newest run of each, so a run that a newer one cancelled, such as the Visual run a label event replaces, does not count; nothing merges while a run is queued or in progress, and `--match-head-commit` refuses a pull request that moved since. A person reads one only when its checks fail. No repository setting or branch rule is needed: the workflow merges with its own token after checking the runs itself, so direct pushes to `main` are unaffected.

Two cases still need a person. A merge made with the workflow's `GITHUB_TOKEN` starts no workflow, so the workflows that run on a push to `main` do not run for it; the next push runs them, or start them with `gh workflow run`. A pull request that edits `.github/workflows/` (a GitHub Actions update) can be refused, because that token has no `workflows` permission; merge it by hand once its checks pass.
